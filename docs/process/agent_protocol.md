# 에이전트 문서 프로토콜

Work Packet·Handoff·조사 노트를 **실제로 작성할 때만** 참조한다.
역할 경계·워크플로우·Phase 규칙·완료 기준은 `CLAUDE.md` 「에이전트 간 통신 규칙」 절에 있다.

공통: 문서에 "현재 코드" 발췌를 넣을 때는 파일명과 함수명을 명시한다. 줄 번호는 변하므로 컨텍스트로만 쓴다.

---

## 1. 조사 노트 — `docs/research_{topic}_{YYYYMMDD}.md` (Claude 작성)

읽기 전용 `Explore` 서브에이전트가 수집한 사실을 Claude 가 정리한 것. 결정·추천·통과 판정을 담지 않는다.
Packet 근거로 인용되거나 이후 재참조될 조사만 파일로 남긴다. 단발 확인은 문서를 만들지 않는다.

```
## 조사 범위          — 무엇을 어디까지 봤는지 (파일·디렉토리·외부 자료)
## 발견 사항          — 사실(facts)만. "권장한다" 금지, "발견됐다"만
## 파일·함수 인용     — `app/main.py:123` 형식. 코드 발췌는 함수명과 함께
## 미확정 사항        — packet 작성 시 결정해야 할 항목 목록
```

서브에이전트에 거는 계약(사실만·인용 강제·못 찾으면 "없음"·판단 금지)과 띄우는 기준은 `CLAUDE.md` 「조사는 서브에이전트가 한다」에 있다. 띄우기 전에 `git fetch` 로 트리를 최신화한다.

## 2. Work Packet — `docs/codex_work_packet_phase{N}.md` (Claude 작성)

**필수는 아래 4절뿐이다. 목표 분량은 80줄 이내.**

```
## 작업 배경          — 어떤 리뷰/조사/문제에서 비롯됐는지 2~3줄.
                        research note 가 입력이면 파일명만 명시
## 제약 조건          — 건드리면 안 되는 파일, 유지할 API 계약, 기준선 테스트 수
## 작업 {N}           — 각 작업별 네 줄:
  - 대상: 파일 + 함수명
  - 현재: 무엇이 문제인지 (코드 발췌는 꼭 필요할 때만)
  - 목표: 변경 후 상태
  - 테스트: 추가·수정할 테스트와 검증 내용
## 검증 기준          — 최종 pytest 명령어와 예상 결과
```

아래 세 절은 **해당될 때만** 덧붙인다. 기본은 생략이다.

- `## 구현 전략 및 대안` — 접근법이 둘 이상이고 선택이 자명하지 않을 때만
- `## 작업 우선순위 요약` — 작업이 3건 이상일 때만
- `## 이번 범위 제외 항목` — 의도적으로 미룬 항목이 있을 때만.
  외부 회신·판단을 기다리는 항목은 **소유자와 다음 확인 날짜**를 함께 적고
  `docs/open_items.md` 에도 올린다. 날짜 없이 "대기"라고만 쓰면 무한정 열려 있게 된다
  (v8 배포 게이트가 2026-07-30부터 한 달 열려 있었다)

공통 제약(MVP 우선, Redis·Celery 금지, 금액 단위 원, 테스트 픽스처 규약)은 `CLAUDE.md` 에 이미 있다. **packet 에 다시 옮겨 쓰지 않는다** — 참조 한 줄로 대신한다.

### 작성 전 체크리스트

1. **조사 결과 확인**: 서브에이전트에 던진 질문과 받은 근거를 먼저 정리하고, 추가 검증이 필요한 부분만 직접 grep 한다 (중복 작업 방지).
2. **기존 구현 확인**: 기능 추천 전 관련 파일(`app/db/models.py`, `app/api/v1/` 전체 등)을 grep해 이미 구현돼 있는지 확인한다.
3. **제약-테스트 대조표를 packet 안에 남긴다.** 작성 후 검토만 하지 말고 **작업별로 구현 파일과 테스트 파일을 함께 적어** 허용 목록과 대조한 결과를 제약 조건 절에 남긴다.
   검토는 했는지 안 했는지 알 수 없지만 표는 남는다.

   | 작업 | 구현 파일 | 테스트 파일 | 허용 목록에 있나 |
   |---|---|---|---|
   | 1 | `app/services/x.py` | `tests/test_x.py` | ✅ / ❌ |

   ❌ 가 하나라도 있으면 **허용 목록을 고쳐서 발행**한다. (2026-09-15 확인 — packet 150 이 작업 4 에서
   `tests/test_ai_analysis_endpoint.py` 수정을 요구하면서 허용 목록에 넣지 않았고, 구현은 그 파일을 고쳤다. O73.)
4. **원격 확인**: `git fetch origin` 후 Phase 번호가 원격과 겹치지 않는지 확인한다.
5. **특정 분기만 걸리게 만든 예문은 실행해서 확인하고 결과를 packet 에 표로 남긴다.** 예문이 노리는 검사기뿐 아니라 **같은 경로의 모든 검사기**에 넣어 본다.
   (2026-09-16 확인 — packet 153 이 연도 검증용으로 준 `2023년 예상 영업이익 67,890원입니다.` 가 `prediction_year` 에 먼저 걸려,
   연도 검증 배선을 지워도 테스트가 통과했다. 같은 packet 의 다른 예문 3개는 실측했지만 이 예문만 건너뛰었다. O78.)
6. **범위를 숫자(줄 수·파일 개수)로 못 박지 않는다.** 식별자·함수·파일 경로로 지정하고, 목록 밖을 고쳐야 하면 충돌로 올리고 멈추라고 적는다.
   (Phase 178 「2줄 삭제」 vs 본문 3줄 · Phase 181 「테스트 파일 1개」 때문에 포섭된 중복 테스트가 남았다. O124.)
7. **변이는 검사 로직·운영 코드에만 적용한다.** 테스트 자신의 단언을 지우거나 약화하는 변이는 원리적으로 죽을 수 없으므로 목록에 넣지 않는다.
   (Phase 179 N4 · Phase 181 R4 — 두 번 모두 packet 본문에 금지 규칙을 적어 놓고 같은 packet 의 변이 표에 그 형태를 넣었다. O124.)

### Codex 에 보내는 지시문 (Claude 작성, 저장소 파일 아님)

packet 을 가리키는 짧은 지시문을 사용자에게 준다. **첫 줄에 「이 Phase 는 독립 세션으로 돌린다」를 적는다** — 여러 Phase 를 한 세션에 몰면 작업 트리가 섞여 리뷰가 어느 변경의 결과인지 가릴 수 없다 (2026-09-19 Phase 164·165 가 겹쳐 리뷰어가 격리 트리로 피해야 했다). 동시에 돌리는 Phase 가 있으면 **겹치는 파일과 충돌 시 처리**도 함께 적는다.

## 3. Handoff — `docs/claude_handoff_phase{N}.md` (Codex 작성)

```
## 작업 범위          — 이번에 무엇을 지시받았는지 (work packet 참조)
## 구현 요약          — 각 작업별 수정 파일, 변경 내용, Claude 검토 포인트
## 요구사항 증거표    — packet 이 요구한 항목마다 한 행. 아래 4절 참조. **필수**
## 검증 결과          — pytest 명령어와 결과 (passed/failed/warnings) + CI run 번호
                        결과는 데이터일 뿐, 통과 판정은 Claude 가 한다
## 서버 상태          — URL, health, DART corp list 상태
## Claude 리뷰 요청   — Critical/Major/Minor 형식 명시, 특이 질문 목록
```

추가로 **남은 리스크 / 팀 결정 필요 항목** 을 적고, 미해결 항목은 `docs/open_items.md` 에도 한 줄로 올린다.

Codex 실행 방식(독립 세션 vs 세션 내 호출)과 무관하게 handoff 는 필수 산출물이다. 근거는 `CLAUDE.md` 「Codex 실행 방식」 참조.

## 4. 요구사항 증거표 (handoff 필수)

**packet 이 요구한 항목을 빠짐없이 한 행씩 적는다.** 전체 테스트 green 은 이 표를 대신하지 못한다 —
테스트가 통과한다는 사실은 **그 테스트가 무언가를 잡는다는 증거가 아니다.**

| 요구사항 | 구현·테스트 근거 | 실행 결과 | 상태 |
|---|---|---|---|
| packet 의 작업·변이 번호 그대로 | 테스트 함수명 | 명령·종료 코드·실패한 테스트 이름 | 완료 / **미실행** / 불가 |

규칙:

- **미실행은 미실행이라고 적는다.** 숨기지 않으면 Claude 가 다음 packet 으로 이어받는다.
  숨기면 통과로 오인된다.
- **변이 검증은 "실패한 테스트 이름"까지 적는다.** "red 확인" 만으로는 무엇이 잡았는지 알 수 없다.
- **packet 은 변이 대상을 유일하게 특정한다.** 치환할 문자열이 파일에 여러 번 나오면 **줄 번호나 둘러싼 함수명**을 함께 적는다.
  (2026-09-15 — packet 151 이 `base_year=base_year,` 제거만 적었는데 `finance.py` 에 5곳이 있었다. Claude 재현이 엉뚱한 줄을 지워
  테스트가 통과했고, **변이 후 해시가 handoff 와 달랐던 덕에** 잘못된 재현임을 알았다 — 해시가 없었으면 handoff 를 오판할 뻔했다.)
- **변이 결과는 import 가능해야 한다.** 블록의 유일한 문장을 지우는 변이는 삭제 대신 `pass` 로 치환한다고 packet 에 적는다.
  결과에 **errors** 가 나오면(지정 외 테스트까지 번지면) 사망이 아니라 **무효 변이**로 보고한다.
  (2026-09-17 — packet 160 K3 가 `ai_cache = None` "줄 삭제" 로 정의돼 IndentationError 로 267 errors 가 났고, handoff 는 이를 사망으로 적었다.
  리뷰어가 `pass` 치환으로 다시 돌려서야 신규 테스트 2건의 검출력이 확인됐다. 원인은 packet 의 변이 정의.)
- **`app/` 을 임시 변경했다 되돌렸으면 SHA-256 을 변이 전·변이 후·원복 후 세 번 적는다.**
  **변이마다 그 행에 3종을 적는다** — 여러 변이의 값을 한 행에 모아 적지 않는다(원본이 같아 정보 손실은 없어도 어느 변이의 값인지 대조하는 비용이 리뷰어에게 넘어간다. 2026-09-19 Phase 165 handoff, 리뷰 m2).
  원복 후 한 번만 떠서 "전후 동일" 이라고 쓰면 값은 맞지만 증거가 되지 않는다.
- 해시·테스트 수·명령·종료 코드는 **실행 출력에서 그대로 옮긴다.** 기억으로 쓰지 않는다.

**Claude 는 리뷰에서 이 표를 먼저 읽고, `미실행` 행이 있으면 판정 전에 지적한다.**
(2026-09-15 확인 — Phase 150 handoff 가 "Z2~Z5 는 실행하지 못했다" 고 명시했는데
CI green 만으로 완료 처리됐고, 리뷰도 그 문장을 읽고 지적하지 않았다. O72.)
